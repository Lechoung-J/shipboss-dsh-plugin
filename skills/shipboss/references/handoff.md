# 工程师的记忆与交接

## 先做这个判断

每次派发前问一句：**这个任务需要工程师记得上一阶段吗？**

| 情况 | 做法 |
|---|---|
| 一轮能做完、自包含 | **无记忆**，独立派发 |
| 长链路、多阶段、后一阶段依赖前一阶段的产物 | **交接文档**（见下） |

判断标准：如果你需要向工程师解释"上次那个是怎么回事"，那就是长链路。

## 交接文档是硬要求，不是可选

长链路任务**必须**让每个阶段产出交接文档，下一阶段工程师先读文档再动手。

三条理由，第三条最关键：

1. **原生 Codex 后端没有记忆。** 官方限制原话：每次运行新建一个进程、
   一个线程和一个轮次，不支持续接、恢复、池化。你没法"续"。
2. **你会换引擎。** 前三阶段用 Codex，第四阶段发现 Claude Code 更合适——
   有交接文档就能直接换人，没有就只能重做。
3. **记忆放在工程师的会话里，你就验不了。** 这直接违反铁律 1。
   会话是不透明的，你看不到里面存了什么、对不对、有没有过期。
   **落盘的文档才是你能读、能 diff、能拿去验收的东西。**

第 3 条是这个设计的根。你要当独立验收方，就不能让被验收方的记忆变成黑盒。

## 交接文档模板

放在 `.delegate/<task-slug>/HANDOFF-<阶段号>.md`。
**建议入库**——它是长链路的记忆载体，git 历史就是它的版本管理。

```markdown
# HANDOFF-1 —— <阶段名>

## 这一阶段做完了什么
- <产物路径>：<一句话>
- <产物路径>：<一句话>

## 关键决定与理由
| 决定 | 为什么 | 被否决的方案 |
|---|---|---|
| 用 A 而不是 B | <原因> | B 因为 <原因> 没采用 |

**这一节最值钱。** 下一阶段最怕的是推翻一个已经权衡过的决定。

## 当前状态
- 能跑：`<命令>` → <结果>
- 不能跑 / 已知坏：<是什么>

## 已知问题与坑
- <问题>：<现象>，<你排查到哪一步>

## 下一阶段的输入
- 从哪开始：<具体文件/函数/行>
- 硬约束：<不能动的接口、不能引入的依赖>
- 建议但未验证的方向：<想法>

## 可复用的东西
- <脚本/测试/数据的位置>
```

### 写作要求

- **写给一个完全没有上下文的工程师看。** 他刚接手，不知道你和老板聊过什么。
- **决定和理由分开写。** 光写"用了 A"没用，要写"为什么不是 B"。
- **诚实写没做完和不确定的部分。** 藏问题会在下一阶段变成返工。
- **不要写成流水账。** "我先读了 X，然后改了 Y" —— 没人关心。
  只写状态和决定。

## 可选优化：会话续接

如果走 CLI 路径，可以复用同一个 Codex / Claude Code 会话：

```bash
codex exec resume --last          # 续最近一次
codex exec resume <session-id>    # 续指定会话
claude -p --resume <session-id>   # Claude Code 同理
```

**这只能当效率优化，不能替代交接文档。** 原因见上文第 3 条。

还有个现实问题：会话有上下文窗口。链路走到第五、第六阶段，
如果全靠续接，工程师每次都在重读全部历史，上下文会膨胀到不可用。
交接文档是**提炼过的**，每阶段只带必要信息——这本身就是上下文卫生。

## 什么时候不要写交接文档

- 一次性任务（一轮做完）
- 阶段之间没有依赖
- 产出本身就是文档（那它已经是交接件了）

**不要为了流程完整而无脑生成文档。** 写一份没人读的交接文档，
和写一份没人读的测试一样，只是浪费。

## 反模式

| ❌ | 为什么 |
|---|---|
| 靠工程师的会话记忆传递上下文 | 黑盒，你验不了 |
| 交接文档写成流水账 | 下一阶段读完还是不知道从哪开始 |
| 只写"做了什么"，不写"为什么" | 下一个工程师会推翻你的决定重做一遍 |
| 隐瞒没做完的部分 | 问题延后暴露，返工成本翻倍 |
| 每阶段都硬造一份文档 | 浪费，且淹没真正重要的那一份 |
| 交接文档不入库 | 丢了就没了，且无法 diff 出哪一版是对的 |
