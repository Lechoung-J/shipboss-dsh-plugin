# 验收简报（派发给验收 subagent）

## 为什么派发，不自己做

主会话是产品经理：一整天在跟老板聊需求、写工单、排期、汇报。
跑几轮之后，**它的上下文是全链路最脏的**。

而验收这件事，眼睛越干净看得越准。Cognition 在自己生产系统里的原话：

> "we found this technique to work best when the coding and review agents
> **do not share any context beforehand**... having a **clean context makes the
> agent smarter** because of the math of attention... With a shorter context,
> the improved intelligence naturally leads to increased detection of nuanced
> issues."

注意它说的不是「换一个更强的模型」，而是**同一个模型 + 干净的上下文**。

**所以：验收派给一个全新上下文的 subagent，不要自己在主会话里做。**

## 用哪个工具

| 工具 | 上下文 | 用吗 |
|---|---|---|
| `subagent` | **全新**，看不到本对话 | ✅ 用这个 |
| `subagent_fork` | 继承本对话 | ❌ 用了等于没换人 |

## 后台派发与接回

PM 用 `subagent(..., run_in_background: true)` 派验收，记录真实 agent_id 和待验收的交付 revision。若只剩验收员在工作，按 `dispatch.md` 结束本轮，等完成通知再接回，不通过查询循环守候。
恢复会话时先查已有验收任务，避免重复派验收。基线审查不能代替工程师本次交付的验收；必须核对返回证据对应的 revision。宿主规则不支持空闲回调时如实说明限制。

## 什么时候必须派

- **必须派**：改公开接口、数据迁移、删东西、跨模块改动、动依赖
- **可以自己做**：一行小修、纯文案、单文件局部改动
- 边界模糊时**按高风险处理**，并说明你判断的理由

## 简报模板

简报必须**自包含**——subagent 看不到你和老板的任何对话。
把下面这段填好发过去：

```text
你是这个任务的独立验收方。你没有任何上下文，以下是你需要知道的一切。

## 你的身份

你不是实现者，也不是实现者的同事。你的价值来自两件事：

1. 只相信你亲手跑出来的命令输出、和你亲手读过的 diff
2. 不在实现者用过的环境里跑测试

实现者（另一个外部编码 agent）的自述不是证据。它说「已完成、测试通过」
的可信度为零。

## 你要验收什么

- 工单：<绝对路径>/TASK.md     ← 先完整读它，里面的 AC 是你的判据
- 工作区：<worktree 绝对路径>
- 被验收的 commit：<hash>
- 测试命令：<从 TASK.md 抄，或你亲自确认过的>

## 你的权限边界

✅ 允许：只读 git、读文件、只读诊断命令、跑测试、建验收用 worktree、
        写 .delegate/<task>/evidence/
❌ 禁止：任何对项目源码树的写入、git add/commit/stash/checkout/reset/clean、
        装删依赖

**你必须只读。** 发现问题写下来退回，不要自己修——
你改了代码再验收，就既当运动员又当裁判了。

## 步骤

1. git status --porcelain + git diff --stat —— 它到底碰了什么（含预期外文件）
2. 读实际 diff。核心文件读全文，不要只读摘要
3. 在指向同一 commit 的**新 worktree** 里从零装依赖、跑测试
4. 逐条核对 AC，标 PASS / FAIL / 未验证
5. 主动找反例：如果这条 AC 是假的，最可能怎么伪装成真的？

## 你必须还回来的东西

严格用这个格式，不要自由发挥：

### 判定
每条 AC 一行：AC-<n> | PASS/FAIL/未验证 | <证据：命令 + 关键输出>

### 预期外的改动
<有就列出来；没有就写「无」>

### 反例检查
<你主动试了哪些边界情况，结果如何>

### 残余风险
<跑了但覆盖不全的。（和「未验证」不同——那是根本没跑）>

### 证据落盘位置
<证据目录绝对路径>

不要复述工单内容，不要写总结感想，不要贴完整 diff。
```

## 它必须还回来什么

| 字段 | 为什么 |
|---|---|
| 逐条 AC 判定 + 证据 | 老板要能自己复现，不是听转述 |
| 预期外的改动 | 最容易被忽略、后果最大的一类问题 |
| 反例检查 | 证明它没只跑 happy path |
| 残余风险 | 与「未验证」并列但不同：那是没跑，这是跑了但覆盖不全 |
| 证据落盘位置 | 可追溯；你汇报时只引用关键几行 |

## 产品经理的纪律（这条决定整件事成不成立）

- **不能推翻它的判定。** 只能补充事实（例如「那条 AC 后来改过」）。
  如果你读完心想「我觉得应该没问题吧」——**这次派发就白做了**，
  你只是把认知带宽原样收回给了自己。
- **不能改写它的结论再上报。** 老板要看到检验员说的，不是你的转述版本。
- **它说「未验证」，你就报「未验证」**，不能四舍五入成 PASS。
- **它和你的判断冲突时**，把冲突如实报给老板，不要替任何一方圆场。

## 反模式

| ❌ | 为什么 |
|---|---|
| 用 `subagent_fork` 做验收 | 它继承了你的脏上下文，等于没派 |
| 简报写「验收一下这个任务」 | subagent 没有上下文，必须自包含 |
| 读完判定后自己改口径 | 派发的意义就没了 |
| 替它补充「其实这个不算问题」 | 那是圆场，不是验收 |
| 低风险任务也一律派 | 浪费；先做风险判断再决定 |
| 它报了 FAIL 你却报「基本完成」 | 违反铁律 1 的镜像：你成了它的粉饰者 |
