# 验收协议

这是整个流程里唯一不能被跳过、不能被压缩的部分。
老板的信任建立在这里，不建立在工程师的自我报告上。

**默认动作**（老板已明确选择：跑测试 + 看 git diff）。

---

## 谁来验收：派一个全新上下文的 subagent

**默认不要自己在主会话里做。** 主会话是产品经理，一整天在跟老板聊需求、
写工单、排期、汇报——跑几轮之后**它的上下文是全链路最脏的**。

Cognition 在自己生产系统里实测：验收方与实现者**不共享任何上下文**时效果最好。
同一个模型 + 干净上下文，就能显著提升细节检出率。不是要换个更强的模型，
是**换一双没被今天这一整天污染的眼睛**。

| 场景 | 做法 |
|---|---|
| 改公开接口 / 数据迁移 / 删东西 / 跨模块 / 动依赖 | **必须派** |
| 一行小修、纯文案、单文件局部改动 | 可以自己做 |
| 边界模糊 | 按高风险处理，并说明理由 |

派发用 `subagent`（**全新上下文**），**不要用 `subagent_fork`**
（它继承本对话，等于没换人）。简报模板见 `references/verification-brief.md`。

> ⚠️ 派发之后，**你不能推翻它的判定**，只能补充事实。
> 如果你读完心想「我觉得应该没问题吧」——这次派发就白做了。

下面的步骤既是验收标准，也是 subagent 的执行规程。写简报时对照着写。

---

## 验收方的权限边界（先读这条）

**验收时你不能碰源代码。** 发现问题就写返工单退回，不要自己上手改。

理由不是「不信任你」，而是三条硬的：

1. **你改的地方没经过任何人审查**——一个没被验收过的改动，混进了「验收通过」的结论里
2. **你既当运动员又当裁判**——下一轮你没法中立地验收自己动过的东西
3. **出问题分不清是谁的活**——追溯链断了

「独立验收方」这个身份一旦破了，就再也修不回来。

### 这条约束能做什么 / 不能做什么

**✅ 允许**

- 只读 git：`git status` / `diff` / `log` / `show` / `blame` / `stash list`
- 读文件：read / grep / glob
- 只读诊断：`ls` / `stat` / `wc` / `head` / `tail` / `find`
- TASK.md 里定义的**项目测试命令**
- 写 `.delegate/<task>/evidence/` —— 那是你的工作记录，不属于交付物
- 建验收用的新 worktree（见步骤 3）—— 那是环境准备，不是改产出

**❌ 禁止**

- 任何对**项目源码树**的写入：edit、write、重定向覆盖
- `git add` / `commit` / `stash` / `checkout` / `reset` / `clean`（会改变工作区状态）
- 装、删、升级依赖
- 「顺手修一下」——哪怕是一行、哪怕你确信他是对的

**⚠️ 唯一例外**：如果测试根本跑不起来（缺测试夹具、缺环境变量），
**停下来**，把它写进 `TASK.rev2.md` 交给工程师，不要自己补。
你补的夹具会变成「你自己写的测试自己跑」，那就不叫独立验收了。

## 步骤 1 — 它到底碰了什么

```bash
git -C <wt> status --porcelain
git -C <wt> diff --stat
git -C <wt> diff --stat --cached      # 若它用了 add
```

看三件事：
- **预期内的文件**是否都改了。
- **预期外的文件**（配置、锁文件、无关模块、测试被删）——每一个都要问为什么。
- **该改却没改的**文件。

危险信号，立刻升级调查：
- `pnpm-lock.yaml` / `package-lock.json` / `requirements.txt` 无理由变动
- 测试文件被删除或整体注释掉
- `.gitignore`、CI 配置、`.env` 类文件被改
- 出现你没要求的新依赖

## 步骤 2 — 读实际 diff

```bash
git -C <wt> diff -- <核心文件>          # 核心逻辑逐个读全文
git -C <wt> diff | head -n 400          # 其余扫一遍
```

- **核心文件读完整 diff，不要只看统计。**
- 边界条件、错误分支、资源释放、并发，逐个看。
- 特别注意「看起来对但绕过了问题」的写法：
  - 把断言放宽以让测试通过
  - `try/catch` 吞掉异常
  - 硬编码返回值匹配测试用例
  - 用 `any` / `# type: ignore` / `eslint-disable` 消掉报错
  - 删除或 `.skip` 掉失败测试
  - 修改测试的期望值而不是修实现

## 步骤 3 — 在干净环境里跑测试

**不能在工程师用过的那个工作区里跑。** 那里散落着他的构建产物、依赖、
缓存。你可能测出「通过」，而真正起作用的是上一批的残留——**你测的不是这一版
代码，是他的工作台。**

```bash
T=<task-slug>
COMMIT=$(git -C <wt> rev-parse HEAD)
echo "$COMMIT" > .delegate/$T/evidence/commit.txt

# 先看他留下了什么（dry-run，不删任何东西）
git -C <wt> clean -xdn | head -30

# 在别处开一个指向同一 commit 的干净工作区
git -C <wt> worktree add /tmp/verify-$T "$COMMIT"

# 在新工作区里从零装依赖、跑测试
cd /tmp/verify-$T && <装依赖> && <测试命令>

# 收尾
git -C <wt> worktree remove /tmp/verify-$T
```

铁律：
- **不接受「我跑过了」。** 你必须自己跑。
- **必须记录 commit hash。** 证据的价值取决于它对应哪一版代码。
  在一个已经变了的树上跑绿，等于没跑。
- 先确认测试**在改动前是绿的**（否则你不知道是新失败还是老失败）。
  必要时在新 worktree 里 `git stash` 后跑一次基线。
- 逐条执行 AC 里写的验证命令，**包括失败路径那条**。
- 新写的测试要确认它**真的会失败**：把实现临时改回错误行为，看测试是否报红。
  不会失败的测试等于没有测试。

> 这一步有成本：依赖要重装、测试要重跑，一次验收可能从 1 分钟变成 5 分钟。
> **这个成本必须付。** 省下它，你拿到的「通过」可能是假的——
> 而假的通过比没有通过更贵。

## 步骤 4 — 逐条判定 AC

| 状态 | 含义 |
|---|---|
| PASS | 你在干净环境里亲自跑了验证命令，看到期望结果 |
| FAIL | 跑了，结果不符 |
| 未验证 | 你没能跑（环境缺失等）——**必须显式标为未验证，不能算 PASS** |

「未验证」在汇报里必须出现，不能静默省略。老板有权知道自己承担了什么风险。

## 步骤 5 — 对抗性复核

**主动假设工程师优化了指标而不是解决了问题。**

逐条问：
- 如果这个 AC 是假的，最可能怎么伪装成真的？
- 我有没有只测了 happy path？错误输入、空输入、超大输入、并发呢？
- 它有没有为了让测试通过而收窄了功能？
- 需求里没说但用户会遇到的场景，它处理了吗？
- 依赖是否引入？许可证是否可接受？
- 这个改动会不会破坏别处？（跑全量测试，不只跑新测试）

发现问题就**再派一轮修**（`TASK.rev2.md`），不要自己动手改。
理由见开头的「验收方的权限边界」。

## 结论怎么下

- **PASS** — 所有 AC 在干净环境里亲自验证通过，无预期外改动。
- **PASS WITH CAVEAT** — 核心 AC 通过，但有未验证项或已识别的小风险。
  必须在汇报里点名。
- **FAIL** — 有 AC 未通过。写 `TASK.rev2.md`，不要向老板汇报为「基本完成」。

**如果你是把验收派给了 subagent**：上面三档由它下，你只负责**原样转达**。
- 不能改口径、不能四舍五入、不能替它圆场
- 它和你的直觉冲突时，把冲突如实报给老板，让老板判断
- 你对结论有异议，**再说一遍事实**让它重新看，而不是自己改判

## 记录

把关键命令与输出存进 `.delegate/<task>/evidence/`：

```
evidence/
├── commit.txt              # 被验收的确切 commit hash（证据的锚点）
├── codex-events.jsonl      # 派发时的原始事件流（不读进上下文）
├── last-message.txt        # 工程师的最终答案
├── diff-stat.txt           # git diff --stat 输出
├── diff.patch              # 完整 diff
└── test-output.txt         # 你在干净环境里跑测试的完整输出
```

汇报里只引用其中的关键几行。**让证据可追溯，但不让它淹没老板。**
