# TASK.md 模板

复制以下结构到 `<project>/.delegate/<task-slug>/TASK.md`，填实。

````markdown
# <任务名>

## 意图（老板原话）
> <原样引用老板的说法，不要改写成技术语言。这是意图的真源。>

## 成功是什么样子
<用老板能看懂的话描述终态。一段以内。>

## 背景与约束
- 仓库：<绝对路径>
- 分支 / worktree：<branch 名 或 worktree 路径>
- 技术栈：<语言、框架、包管理器>
- 测试命令：`<项目实际可跑的命令>`
- 硬约束：<不能碰的文件 / 不能引入的依赖 / 性能或兼容要求>
- 假设：<你替老板做的判断，明确标注，便于它被推翻>

## 交付物
- [ ] <可验证的产出 1，例如「src/parser.ts 导出 parseConfig，处理 X 格式」>
- [ ] <可验证的产出 2>
- [ ] 新增/更新的测试覆盖上述行为

## 验收标准（AC）
每条必须有可执行的验证方式。写不出验证方式的，移到「备注」。

| ID | 标准 | 验证方式 |
|---|---|---|
| AC-1 | <可观察的行为> | `<命令>` |
| AC-2 | <同上> | `<命令>` |
| AC-3 | 不破坏既有行为 | `<全量测试命令>` |
| AC-4 | <错误路径的行为> | `<命令 + 期望的失败输出>` |

## 明确不做（non-goals）
- <防止工程师顺手扩大范围。写出来能省一轮返工。>
- 不要重构 <模块>。
- 不要改动 <文件> 的公开接口。

## 完工时要报告什么
1. 改动的文件清单与一句话说明
2. 每条 AC 你是怎么验证的（贴命令与输出）
3. 你没做到或不确定的部分

## 备注
<无法写成 AC 的期望、设计偏好、参考实现链接。>
````

## 写 AC 的自检清单

派发前逐条过一遍，任何一条答「否」就不要派发：

- [ ] 把 AC 单独拎出来，工程师看不到「意图」段落，也能照着做对吗？
- [ ] 每条 AC 都有具体命令或可观察事实，而不是「代码质量好」「性能合理」？
- [ ] 包含了至少一条**失败路径 / 边界条件**的 AC？
- [ ] 包含了一条**回归** AC（不破坏既有行为）？
- [ ] non-goals 写了？范围蔓延是返工的头号原因。
- [ ] 测试命令是你**实际跑过一次**的，不是猜的？

## 常见退化写法

| 退化写法 | 问题 | 改法 |
|---|---|---|
| 「实现登录功能」 | 无法验收 | 「POST /login 正确凭证返回 200+token；错误凭证返回 401 且不泄露用户是否存在」+ 逐条命令 |
| 「性能优化」 | 无法验收 | 「bench 脚本的 p95 从 <基线> 降到 <目标>，命令：`<cmd>`」 |
| 「修复 bug」 | 无复现 | 「`<复现命令>` 从失败变为通过，且新增的回归测试覆盖该场景」 |
| 「代码整洁一些」 | 不是交付物 | 删掉，或降级为「备注」 |
