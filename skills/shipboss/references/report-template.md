# 一页纸汇报模板

这是老板**唯一**会读的东西。写它的标准是：
**老板读完能做出需要的决定，且不需要回头问你任何问题。**

写进 `REPORT.md`，并在对话里直接把内容作为回复给出（不要只给文件路径）。

````markdown
## <任务名> — ✅ 完成 / ⚠️ 带保留完成 / ❌ 未通过

**一句话结论**：<做成了什么，或卡在哪。这句话要能单独成立。>

### 改了什么
- <文件/模块>：<一句话>
- <文件/模块>：<一句话>

（不复述过程，不贴 diff。）

### 验收证据
| AC | 结果 | 证据 |
|---|---|---|
| AC-1 | ✅ | `<命令>` → <关键输出一行> |
| AC-2 | ✅ | `<命令>` → <关键输出一行> |
| AC-4 | ⚠️ 未验证 | <为什么没跑成> |

测试：`<命令>` → **<N> passed / <M> failed**（<耗时>）

### 风险与未覆盖
- <真实存在的风险，一句话一条。没有就写「无」。>
- <未验证项，以及它意味着什么。>

### 需要你决策
<通常是 0–2 条。没有就写「无，可以继续」。>

1. <需要老板做业务判断的问题 + 你推荐的选项与理由>

<其余都可以由你决定的事，不要列在这里。>
````

---

## 写作规则

**必须**
- 结论放第一行。老板可能只读这一行。
- 证据用「命令 → 结果」，让老板能自己复现。
- 未验证项必须显式出现，不能静默省略。
- 用老板的语言（业务词汇），不是你的语言（技术词汇）。

**禁止**
- 贴 diff、贴日志、贴堆栈。老板要看的是你的判断，不是原始数据。
- 「基本完成」「差不多」——只有三档结论，没有中间态。
- 把「我做了什么」写成流水账。老板关心「现在是什么状态」。
- 「需要决策」超过 3 条。超过就说明你在把工程判断推回给老板。
- 未经自己验证就转述工程师的结论。

**「需要你决策」的正确用法**

✅ 该问：涉及业务取舍、成本、用户体验、优先级、对外承诺的问题。
❌ 不该问：技术选型、命名、目录结构、要不要加测试、用哪个库、
   怎么修这个 bug —— 这些是你的工作。

判断标准：**如果这个问题你自己拍板错了，代价是重写代码；
如果老板拍板错了，代价是业务受损 —— 才问老板。**

## 并行多任务时的汇报

多个任务同时结算时，**先给一张汇总表**，再按需要展开：

````markdown
## 三项目进度

| 任务 | 状态 | 一句话 |
|---|---|---|
| <项目 A / 任务> | ✅ | <结论> |
| <项目 B / 任务> | ⚠️ | <结论 + 保留点> |
| <项目 C / 任务> | ❌ | <卡在哪，已派 rev2> |

**需要你决策**（跨项目的，共 1 条）：
1. <...>

--- 以下按需展开 ---
### <项目 A / 任务> 详情
<上面的一页纸模板>
````

老板先看表，只有想深入的才读详情。这就是认知带宽的分层。

## 中途汇报（工程师完成通知打断了正在进行的对话时）

**通知已到达与任务仍在运行是两回事。** 派发后若只剩等待，PM 应以简短 final 结束本轮；不为等通知保持运行，不循环查状态。
宿主支持完成唤醒时，空闲 PM 可由完成事件开启后续轮次；PM 忙时则在可处理的步骤边界接收通知。先答完老板当前问题，再安排收结果与验收。
此规则不能覆盖宿主强制收齐结果或自动 goal 续轮的要求；存在冲突时按 `dispatch.md` 报告限制，不承诺一定空闲。

**纪律**：

1. **先答完老板当前的话题。** 不要因为通知而改变这一轮的走向，
   也不要把工程师的汇报当成这一轮的主线。
2. **汇报放在回复的最后一段**，用分隔线明确切开。
3. **不要打断老板。** 如果老板的话还没说完，或你还在执行他的要求，
   汇报只能出现在末尾，不能占据开头。
4. **简版优先。** 中途插进来的汇报只给结论和需要决策的项，
   细节等老板问了再展开。

写法：

```markdown
<老板当前话题的正常回答，完整说完>

---

**任务状态：W-003 的工程师已交付，尚待验收。** <若已派验收员，说明已派；否则说明待验收。>
<验收员仍在运行且没有其他可立即推进事项时，到此结束本轮；不在窗口里等待。>
```

**验收没做完就不要汇报成「完成」。** 通知到达 ≠ 任务完成。
你可以先告诉老板"收到了、正在验收"，而不是抢着下结论。

这一条和铁律 1 是一回事：**没验收过的完成，不算完成。**
