# PM 换班：自动存进度，必要时才换窗口

这是产品经理会话之间的交接，区别于 handoff.md 的工程师阶段交接。
目标是长时间自主推进，同时避免上下文耗尽后失去任务状态。不要每张工单都要求老板换窗口。

## 1. 平时自动保存，不打扰老板

在派发成功、收取完成结果、验收结算、确定返工或老板改变授权范围后，增量更新已有 BACKLOG、RUN、REPORT 等记录。不要把完整对话或日志复制进去。
维护 `.delegate/PM-STATE.md` 作为简短索引：目标、已批准范围、关键决定、当前任务及记录路径、下一步、当前调度者与交接状态。
若项目已有等价记录则复用，避免两套状态互相矛盾。

更新这些文件是正常工作，不需要老板确认，也不意味着要换窗口。后台没有新事件时仍按 dispatch.md 待命，不为写检查点而定时唤醒或轮询。

## 2. 换窗口的触发条件

优先使用宿主提供的当前上下文用量/限制；不是累计 token、缓存读取累计量或文件大小。不能可靠取得指标时写「余量未知」，不能编造百分比或扫描其他会话来估算。

有可靠指标时，初始参考策略：
- 低于约 70%：继续正常派发，完成一张工单不触发换班。
- 约 70%：检查状态记录是否足够接班，减少读入大输出，评估下一阶段所需余量；不立即要求老板换窗口。
- 约 80% 且预计下一阶段可能超过余量：进入收尾模式，在最近的安全交接点换班。
- 宿主提示即将耗尽、请求已因上下文过长失败，或不足以安全收取结果：提前做紧急交接，不硬撑到阈值。

70%/80% 是可调整的初始启发式，不是平台保证或每轮必查指标。压缩后若余量已恢复且还没发布交接，可继续工作；不要因为经历一次压缩就要求换窗口。指标未知时依宿主明确预警、最近阶段的实际增长及恢复难度判断，不按固定工单数/固定时间换班。

## 3. 正常交接点与停止派发

进入收尾模式后：
1. 暂停启动新工单和下一轮返工；保留待办，不取消正在工作的工程师。
2. 通过原完成通知收齐本批工程师、验收员的结果；能在余量内完成验收则完成，否则明确留作待验收。不要为交接而同步等待或反复查状态。
3. 理想交接点是本批结果和验收结论已落盘，已准备好下一张工单/返工要求。验收 FAIL 也可以交接，不必一直修到 PASS。
4. 发布交接前核对本会话管理的后台任务，不能只确认其中一个已返回。正常交接应无仍运行或状态不明的任务。
   若确有 running / unknown 任务，交接文档必须逐条列出：`job_id` 或 `agent_id`、owner、`argv`、cwd、
   最后已知状态（`running` / `unknown` / `interrupted-before-terminal`）、现有证据路径，
   以及**下一任不得做什么**（不重派、不删现场、不虚填退出码）。见 `runtime-evidence.md`。
5. 将 PM-STATE 标为 handoff-ready，明确旧 PM 已停派。产出交接文档和开场提示词，只提醒老板一次，随后结束本轮。

发布 handoff-ready 后，旧 PM 不因迟到通知或 goal 续轮再次派发。重复通知核对后只补记录；收到新业务要求时先确认由哪个 PM 负责。Skill 是协作约定，不是跨会话原子锁；不能保证两个并行窗口自动互斥。
已有 goal 如妨碍停派，按用户授权和宿主规则暂停/处理；不能把未完成业务目标标为完成，也不能声称仅靠交接文档就停掉了自动续轮。

## 4. 交接文件：少而完整

每次正式换班写 `.delegate/pm-handoffs/<交接编号>.md`，配套 `<交接编号>-prompt.txt`。不要用覆盖旧版本的方式丢失交接证据。
交接正文建议控制在约 1–2 页，保留关键决定与限制，大日志仅给路径；必要细节链接到现有工单。

模板：

```markdown
# PM 交接 <编号>
- 状态：handoff-ready / emergency-incomplete
- 时间、项目绝对路径、Skill 版本：
- 旧 PM 会话标识（可获得时）、旧 PM 是否停派：
- 换班原因、上下文指标及来源（不可得则未知）：

## 老板的目标与已批准范围
业务动机、成功标准、优先级原则、明确禁区、批准记录的位置。
区分已批准、建议但未批准、被否决的方案；不让老板重新解释已决定的内容。

## 当前交付状态
每张未结工单：ID、阶段、规格版本、基线/交付 commit、worktree、
有无未提交内容、验收结论、证据路径、已完成但不可重复执行的操作。
待办队列给路径；不要把过程日志抄进来。

## 工程师与验收员
所属旧会话、job_id/agent_id、工程师 session/thread ID（若有）、
日志与最终结果路径、最后核对时间、运行/完成/失败/未知状态。
正常交接必须明确「无仍运行或状态不明的后台任务」。

## 下一步
接班后的首个具体动作、依赖、剩余阻塞、真正需老板拍板的问题（没有就写无）。
已确认的环境条件与测试命令；凭据只给安全存放位置，不抄值。
```

提示词必须填入真实绝对路径，不让老板自己拼路径：

```text
/shipboss 请接任这个项目的 PM。
先读取 <交接文档绝对路径>，再按需读取其中引用的工单和运行记录。
延续已批准的目标、优先级和验收标准；不从头规划，不重复已完成工作。
先核实交接版本、代码状态、旧 PM 停派状态及后台任务，再接管调度。
旧会话的 job/agent ID 不代表你能操作它；不假定回调已迁移。
状态一致且无旧执行者冲突时，登记你为当前 PM，执行交接中的下一步。
存在冲突先报告具体冲突，不擅自覆盖成果。继续使用后台派发、完成通知接回和独立验收。
```

对老板只输出：换班原因一句话、交接文档链接、可直接复制的提示词。无需让老板读日志或重新批准已有计划。

## 5. 新 PM 接班

1. 先读交接和必要索引；逐项核对关键 commit、工作树状态、未验收成果及工单阶段。交接文档是线索，不是免核实的事实。
2. 确认读的是最新交接，旧 PM 已停派；若另一个新 PM 已登记接管，不同时争抢调度。
3. 状态一致后在 PM-STATE 登记交接编号、接班者标识（若可得）和接班时间，继续授权范围内的工作。不要重问已拍板业务问题。
4. 无需搬运旧窗口全部聊天历史。验收引用实际交付版本，不能拿基线审查替代交付验收。

## 6. 紧急交接与后台任务归属

上下文即将耗尽且仍有任务运行时，先尽可能保存状态并标 emergency-incomplete。明确哪些状态未确认、哪些结果待收取；不要宣称正常交接完成。

**旧窗口的 job 回调不会因复制文档自动转给新窗口，子 agent 也不一定可由新会话控制。** 新 PM 不能凭旧 ID 直接认领，更不能因查不到旧 job 就重派一个写同一目录的工程师。
按 dispatch.md 恢复协议核对产物和执行者；只有宿主确实提供且验证过的重接能力才能使用。否则明确说明需旧窗口收尾或用户协调。保留成果，不自动杀进程、不自动丢弃改动。

已有检查点能帮助异常断开后恢复，但本 Skill 不保证自动开新窗口、任务所有权迁移或跨重启持续运行。
